# 06 · 经验教训（Lessons Learned）

> 收尾过程组（Closing）产物：把踩过的坑变成可复用的知识。

## 三条核心教训

### 教训 1：先查契约，再写代码（对应风险 R1）
- **现象**：客户端 `useSessions()` 无参调用导致渲染崩溃，首版即废。
- **本质**：平台钩子有精确签名（`SnapshotSelectorHook` 必须传选择器），凭感觉调用 = 未做技术调研就开工。
- **行动**：开发任何平台能力前，先查运行时契约（本项目的 `cordis_inspect_*` 系列就是干这个的）；不确定就查源码。

### 教训 2：动态 ≠ 持久，交付前先确认生命周期（对应风险 R2）
- **现象**：动态插件随 DSH 进程重启全部丢失，用户"刷新后没有了"。
- **本质**：动态插件按设计是进程内临时物，官方文档明确写着"definitions do not survive a process restart"——这是调研阶段就该登记的风险（R2）。
- **行动**：任何要"常驻"的能力，一开始就要选对载体（宿主组合静态插件），而不是先用临时方案再返工。

### 教训 3：变更也要做影响评估（对应风险 R3/D3）
- **现象**：自动收缩改动后，若不了解"HMR 被禁用"这一部署事实，用户会一直看到旧版并认为没修好。
- **本质**：发布 ≠ 代码写完；还要知道"怎么让用户拿到新代码"（硬刷新/重启）。
- **行动**：每次变更回答三个问题——**改哪端？（宿主/客户端）要不要重启？用户怎么拿到？（刷新/硬刷新/重启）**。本项目已把这三问固化进 `docs/07` 的变更流程。

## 做得好的地方（继续保持）

1. **数据真实性**：术语检测、工具活动、权限快照全部来自真实运行时，不写假数据——这是用户信任的根基。
2. **成本意识**：词库秒出零 token + 模型按需调用，是设计阶段就定的成本控制。
3. **验证闭环**：每次发布前都有可复现的冒烟测试脚本（已归档到 `docs/04`）。
4. **风险对冲**：解释功能有纯词库兜底，模型挂了 UI 不崩。

## 下一次迭代前必读

- 若涉及客户端改动：先读 `docs/07` 的发布流程（HMR 禁用 → 硬刷新）。
- 若涉及宿主改动：确认是否需要重启 DSH，并在 CHANGELOG 注明。
- 若涉及新平台能力：先跑 `cordis_inspect_list` 查契约。
